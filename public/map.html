1 · Architecture

The browser renders screens; it never changes data itself. Every action is posted to the API as a command, run through the engine, and written to the store only if every rule passes.

SME portal · AD2 portalpublic/app.html, public/js/*

One single-page app. The signed-in role decides the portal, the navigation and which actions render. Screens poll every 5 seconds, so a checker sees a maker's work arrive without reloading.

↓ HTTPS · signed session token · JSON commands
APIapi/*.js → server/app.js

/api/session sign-in · /api/state the caller's view · /api/command run one action · /api/status public tracker · /api/reset reseed (passcode). Vercel serverless functions; node server.js locally.

↓
Enginepublic/engine.js

The system of record's rules: role capabilities, four-eyes, the purpose-code and document policy, rate recomputation, bill reservation, balances, the allocation ledger, audit and notifications. Also returns each user only the data their role may see.

↓ read → run → conditional write (replayed on conflict)
Storeserver/store.js

Supabase Postgres in production (one row, reached over HTTPS; Vercel Blob also supported), a JSON file locally. Writes are optimistic: if another user wrote first, the command is replayed on the fresh state, so two people acting at once never overwrite each other.

Simulated servicesclearly labelled in the app

FX reference rates, SWIFT MT103 release and UTRs, PennyDrop, sanctions screening, document AI, SFTP and SAP. Uploads record the file name and size only — file contents never leave the user's device.

5 · Roles and four-eyes

Capabilities are checked by the engine on every command. On top of the role, one person may not act at two stages of the same record: whoever raised a request cannot verify it, the verifier cannot authorise, and the authoriser cannot release.

6 · Controls the platform enforces

ControlHow
AuthenticationSigned session tokens (HMAC-SHA256, 12 hours). Self-registered businesses set a password, stored as a salted scrypt hash. Demo accounts use a shared passcode that can be changed per deployment. Sign-in throttled after 20 failures per 10 minutes.
AuthorisationRole and business re-read from the stored login on every request — an approval or role change applies at once and a token can never grant more than its login holds.
Data isolationAn SME's session receives only its own records; AD2 internal notes and pricing remarks never leave the server for SME users; password hashes never leave the server.
RatesA booked rate is recalculated on the server from the approved margin and expires after 48 hours. A deal rate must sit within 3% of the reference rate.
Bills and FIRCsAllocations are capped at what is left after other open payments, disposals and proposals reserve their share — a bill cannot be paid twice, and a FIRC cannot be knocked off twice.
ComplianceEvery outward request and disposal is scored on configurable rules at submission; High needs a reason from the maker and the checker. FEMA and sanctions declarations are required. The SME never sees scores or reasons.
WorkspacesEach role has its own sidebar; a role cannot open another role's screens by URL, and the API refuses anything outside its capabilities. Deactivated users are refused at sign-in and on their next action.
Assisted marginAD2 may price an assisted request only within the configured band below the approved margin; the override is audited.
BalancesRelease debits the INR account and is refused if funds are short; processing a disposal credits it.
InputEvery field is type-, length- and format-checked on the server (PAN, GSTIN, IEC, IFSC, SWIFT, dates, amounts); request bodies are capped.
BrowserContent Security Policy (no inline or third-party script), frame-ancestors self, nosniff, strict referrer, HSTS; every value rendered is escaped.
AuditEvery command writes an audit entry naming the person — and, in an assisted journey, the business acted for.
